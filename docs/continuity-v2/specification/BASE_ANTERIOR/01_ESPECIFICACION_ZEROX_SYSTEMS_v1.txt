
OBJETIVO
Este paquete existe para reanudar Zero'X Store en ChatGPT Work sin empezar desde cero, sin reemplazar archivos innecesariamente y sin perder funciones, diseño, integraciones ni decisiones ya tomadas.

REGLA MAESTRA
Antes de modificar cualquier archivo: INVENTARIAR → ENTENDER → RESPALDAR → CAMBIAR EN PEQUEÑO → VALIDAR → CONTINUAR.
No reconstruir la web desde cero. No sustituir componentes completos si basta un cambio localizado. No eliminar funciones existentes para “simplificar”.

1. IDENTIDAD DEL PROYECTO
Zero'X Store no se plantea como una web simple. Debe evolucionar hacia un ecosistema profesional:
- Zero'X Store: experiencia pública, catálogo, compra y perfil.
- Zero'X Editor: edición visual directa para la cuenta Creator.
- Zero'X Control: panel administrativo privado.
- Zero'X Wallet: saldo interno y libro de movimientos.
- Zero'X Core: pedidos, proveedores, APIs, automatización y reglas.
- Lunes Assistant: futura capa inteligente de operación.

Repositorio conocido: westdark161208-dot/zerox-store
Rama conocida del proyecto Store: main.
IMPORTANTE: antes de escribir, Work debe inspeccionar el estado REAL del repositorio y confirmar estructura, cambios existentes y despliegue. No asumir que esta especificación describe nombres actuales de archivos.

2. PROTOCOLO DE NO DAÑO
Antes de implementar:
1) Leer árbol del repositorio y archivos de configuración.
2) Identificar framework, rutas, componentes, estilos, base de datos y backend actuales.
3) Identificar qué funciones ya existen y dónde viven.
4) Crear un punto de restauración/branch de trabajo antes de cambios importantes.
5) No borrar código funcional sin demostrar que está obsoleto y tener reemplazo validado.
6) No cambiar simultáneamente UI, autenticación, base de datos y pagos en una sola modificación.
7) Mantener secretos fuera del repositorio. Nunca insertar tokens/API keys en frontend o commits.
8) Validar versión móvil y escritorio después de cada cambio visual.
9) Validar login, registro, perfil, catálogo y flujo de compra después de cambios compartidos.
10) Documentar archivos modificados y motivo de cada cambio.
11) Si hay conflicto entre esta especificación y el código actual, conservar primero lo funcional y reportar el conflicto antes de sustituirlo.
12) No alterar producción sin una ruta de rollback.

5. ZERO'X EDITOR
El Editor NO será un dashboard separado. Será un modo de edición sobre la propia tienda.
Solo Creator/roles autorizados pueden activarlo.
Flujo:
Zero'X Store → Activar Editor → seleccionar elemento → editar → previsualizar → guardar borrador/publicar.

Debe permitir, según el tipo de elemento:
- título y subtítulo;
- precio;
- imagen;
- descripción;
- disponibilidad/estado;
- categoría;
- región;
- proveedor asociado;
- orden;
- banners, carruseles y anuncios;
- datos comerciales de fichas.

NO debe editar desde UI:
- arquitectura;
- efectos complejos;
- lógica crítica;
- autenticación;
- APIs/secrets;
- seguridad;
- infraestructura.
Eso seguirá mediante código/Git.

Toda edición debe validarse en backend. Ocultar un botón en frontend NO es seguridad.

7. ZERO'X WALLET
El saldo interno no debe ser solo un número editable.
Implementar concepto de ledger/libro de movimientos.
Cada movimiento debe poder registrar:
- ID único;
- usuario;
- tipo/concepto;
- monto;
- saldo anterior;
- saldo posterior;
- fecha;
- origen;
- pedido/transacción relacionada;
- estado;
- actor/sistema que lo generó.

Evitar modificaciones directas de saldo sin trazabilidad. Diseñar idempotencia para pagos/webhooks para reducir dobles abonos.

8. SEGURIDAD CREATOR/ADMIN
No existe riesgo cero. Usar defensa por capas.
Preferencia:
- Passkey/WebAuthn como autenticación administrativa principal.
- Autenticación reforzada (step-up) para acciones críticas.
- Segundo autenticador/passkey o TOTP como respaldo.
- Códigos de recuperación guardados fuera de la web.
- Correo/SMS/WhatsApp principalmente para alertas o recuperación limitada, no como llave maestra.
- Sesión administrativa separada y de duración limitada.
- Reautenticación para cambios críticos.
- Rate limiting e intentos fallidos controlados.
- Registro de accesos y acciones administrativas.
- Capacidad de cerrar todas las sesiones.
- Notificación al añadir/eliminar credenciales.
- RBAC/roles validados SIEMPRE en backend.
- Cookies seguras HttpOnly/Secure/SameSite cuando corresponda.
- CSRF, XSS, validación de entrada y autorización por endpoint.
- Secrets únicamente en almacenamiento seguro del entorno, nunca frontend/Git.
- No exponer stock privado, proveedores, márgenes, wallet o datos administrativos mediante endpoints públicos.

Acciones que deben requerir step-up:
cambiar credenciales, añadir administradores, modificar métodos de recuperación, alterar destino financiero, retiros/ajustes sensibles, acciones masivas, cambios críticos de proveedor.

9. SECURITY CENTER
Preparar área para:
- dispositivos/passkeys autorizados;
- sesiones activas;
- accesos recientes;
- intentos fallidos;
- cambios administrativos;
- auditoría;
- cerrar todas las sesiones;
- recuperación segura.

10. LUNES ASSISTANT
Reservar integración futura en Zero'X Control.
No conectar ni otorgar permisos amplios hasta diseñar permisos y confirmaciones.
Objetivo futuro:
- consultar pedidos/errores/stock/márgenes;
- resumir estado operativo;
- detectar incidencias;
- proponer acciones;
- ejecutar acciones autorizadas con confirmación para operaciones sensibles.
Lunes no debe tener acceso irrestricto a secretos.
